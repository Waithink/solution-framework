# solution-framework · 解决方案框架编写Skill

> **版本：v6.0** | 面向售前咨询部 · 融合阿信多智能体协作流水线

> **Umbrella说明：** solution-framework 吸收了 axin-pipeline 的四角色协作流水线机制（见最后一节）。axin-pipeline 已归档。

---

## 核心定位

通过**对话式信息收集**，自动生成符合微盟WOS产品体系的**解决方案框架文档**，用于售前阶段向客户/销售展示微盟解决方案能力。

> **注意**：解决方案框架 ≠ SOW文档。解决方案框架是面向客户的方案设计（行业分析、业务模式、产品匹配、价值主张）；SOW是集成对接、定制业务的具体实施说明。两者是完全不同的文档类型，本skill仅负责解决方案框架的编写。

---

## 一、使用场景

| 场景 | 触发条件 | 输出目标 |
|-----|---------|---------|
| **标准方案输出** | 客户有明确需求，销售发起方案请求 | 完整解决方案框架文档 |
| **方案讨论** | 需求不明确，需要探索可能性 | 方案大纲 + 方向建议 |
| **方案评审** | 已有初稿，需要审核优化 | 审核报告 + 修改建议 |
| **方案学习** | 新人学习、行业研究 | 框架模板 + 案例参考 |

---

## 二、四阶段协作流程（核心）

当需求具备以下特征时，自动启动四阶段协作流程：
- 客户规模较大（多门店/多品牌）
- 预算较高（20万+）
- 需求较复杂（多业务模块）
- 客户明确要求详细方案

### 流程图

```
用户输入：行业 + 客户类型 + 业务模式 + 核心痛点
   ↓
① 参谋长（需求分析 & 行业洞察）
   ├── 信息补全追问
   ├── 需求本质挖掘
   ├── 行业背景分析
   └── 方案定位建议
   ↓
② 调度长（框架规划 & 任务分解）
   ├── 按§四动态装配规则组合章节
   ├── 确认重点章节
   ├── 分解任务清单
   └── 设定里程碑
   ↓
③ 执行长（内容生成 & 细节打磨）
   ├── 按框架逐章节生成
   ├── 嵌入微盟产品能力
   ├── 匹配行业案例
   └── 打磨语言表达
   ↓
④ 审核官（质量审查 & 修改建议）
   ├── 逻辑完整性检查
   ├── 产品能力匹配检查
   ├── 合规约束检查
   └── 输出审核报告
   ↓
最终交付：解决方案框架文档
```

### 各阶段职责

| 阶段 | 角色 | 输入 | 输出 | 询问用户确认 |
|-----|------|-----|------|------------|
| **① 参谋长** | 需求分析 | 行业/客户/痛点 | 需求分析报告、方案定位 | ✓ 确认需求理解正确 |
| **② 调度长** | 框架规划 | 需求分析报告 | 方案大纲、重点章节 | ✓ 确认框架方向 |
| **③ 执行长** | 内容生成 | 方案大纲 | 完整解决方案文档 | ✓ 确认核心章节 |
| **④ 审核官** | 质量把控 | 完整文档 | 审核报告、修改建议 | ✓ 输出最终版本 |

## 四、方案框架 · 动态章节装配系统

> ⚠️ **重要原则**：本系统采用「构建块 + 装配规则」，**不预设固定章节结构**。调度长根据客户画像（行业+客户类型+业务模式+核心痛点+预算规模）动态组合章节，每个客户拿到的都是定制化框架。

### 4.1 可用章节构建块

以下为所有可用的独立章节构建块，调度长按需选取、排序、组合。

| 编号 | 章节模块 | 核心内容 | 适用信号 | 来源参考 |
|-----|---------|---------|---------|---------|
| **A** | 行业背景与趋势 | 宏观分析、赛道趋势、消费行为变化 | 任何行业客户，必选 | 知识库行业洞察 |
| **B** | 客户现状诊断 | 客户业务现状、现有系统、核心瓶颈 | 有明确改造需求的客户 | 售前调研 |
| **C** | 目标客群画像 | 核心消费者特征、行为偏好、决策路径 | C端运营型客户（零售/美业/餐饮） | 知识库消费者旅程模板 |
| **D** | 行业痛点全景 | 消费者旅程痛点 + 门店/运营痛点 | 需要说服客户改变现状的场景 | 知识库痛点标准模板 |
| **E** | 业务蓝图设计 | 整体业务架构、链路图、预期效果 | 方案复杂度高（多模块/多平台） | 过往方案架构图 |
| **F** | 全链路数字化运营 | 认知→信任→到店→服务→离店→复购 闭环 | 服务型行业（美业/大健康/汽车） | 六链路模型 |
| **F2** | 全渠道运营 | 多渠道并行、即时零售、商品/库存/订单/营销中台 | 零售品牌方（多平台：天猫+抖音+小红书+美团） | 全渠道2.0跃迁模块 |
| **G** | B端赋能体系 | 总部赋能、门店管理、导购/技师赋能 | 连锁/加盟模式客户 | B端产品能力索引 |
| **H** | 微盟产品能力矩阵 | 产品选型、版本建议、行业专属功能 | 任何客户，必选（交付建议用） | 产品能力索引 |
| **I** | 私域运营体系 | 私域沉淀、触点矩阵、运营SOP | 重视用户运营的客户 | 私域运营方法论 |
| **J** | 会员与积分体系 | 等级、积分、权益、储值、付费会员 | 会员运营型客户（零售/美业） | 会员体系模板 |
| **K** | 营销增长体系 | 营销活动、裂变、直播、短视频、KOL | 追求增长的客户 | 星启GEO/WIMO |
| **L** | AI智能体技术架构 | WAI平台架构、Agent矩阵、AI运营 | 技术敏感型/CTO参与决策 | WAI技术架构模块 |
| **M** | 实施路径与保障 | 分阶段实施、里程碑、交付保障 | 预算50万+或关注落地的客户 | 实施方法论 |
| **N** | 技术架构设计 | 系统架构、数据流、安全合规 | 有自研/集成需求的客户 | 技术架构模板 |
| **O** | 效果评估与ROI | 预期效果指标、衡量方式、分阶段目标 | 注重投资回报的客户 | 过往案例经验 |

### 4.2 装配规则

调度长按以下规则链进行自动装配：

```
STEP 1️⃣：基础层（必选）
  ├── A（行业背景与趋势）→ 所有行业都必须
  └── H（产品能力矩阵）→ 最终必须落地到微盟产品

STEP 2️⃣：诊断层（根据需求成熟度）
  ├── 需求明确 → 跳过诊断层
  └── 需求模糊 → B（客户现状诊断）→ 帮助客户理清问题

STEP 3️⃣：核心层（根据客户类型×行业）
  ├── C2C（服务消费者）→ C（客群画像）+ D（痛点全景）+ F（全链路运营）
  │   ├── 零售品牌方 → C + D + F2（全渠道中台专题）
  │   ├── 美业/大健康 → C + D + F（到店→服务→离店→随访链路）
  │   ├── 汽车/服务 → C + D + F（预约→到店→交付→售后）
  │   ├── **3C数码** → C + D + F（认知→考量→决策→交易→增值链路）+ J + K
  │   │   └── 注：3C数码核心差异——高客单价低频、即时零售为主赛道、
  │   │       消费者认知渠道四阶段演变（门户→搜索→算法→AI对话）、
  │   │       售后服务和设备绑定是增值关键节点
  │   └── 食品零售混合 → D + F（双模式：到店+到家）+ J
  ├── B2B（服务经销商以渠道为主）→ G（B端赋能）+ I（私域）
  │   └── 连锁加盟模式 → G + I + J（B端+私域+会员，强加盟必加N）
  └── 混合型（品牌+渠道）→ C + D + F/G + I + J

STEP 4️⃣：增强层（根据客户关注点，可多选）
  ├── 重视增长 → K（营销增长体系）
  ├── 技术敏感 → L（AI技术架构）
  ├── 关注落地 → M（实施路径）
  ├── 有自研需求 → N（技术架构）
  └── 注重ROI → O（效果评估）

STEP 5️⃣：收束层（建议）
  └── E（业务蓝图）→ 方案复杂时加入，展示全局
```

### 4.3 章节排序原则

```
① 认知建立 → ② 问题诊断 → ③ 客群与痛点 → ④ 方案核心（链路/中台/私域等）
⑤ 产品落地 → ⑥ 运营配套 → ⑦ 实施保障 → ⑧ 预期效果

即：A → B(可选) → C/D → (F/F2/G/I/J等核心) → H → (K/L/O增强) → M(可选)
```

### 4.4 典型装配示例

| 客户画像 | 装配结果 | 说明 |
|---------|---------|------|
| **零售品牌（50+门店，全渠道）** | A → D → F2 → J → H → K → M | 先讲行业趋势→痛点→全渠道中台（重点）→会员→产品→增长→路径 |
| **美业连锁（10家店，服务型）** | A → C → D → F → G → J → H → I | 客群画像先行→服务链路→技师赋能→会员→产品→私域 |
| **大健康社区店（客群为老年人）** | A → C → D → F（随访链路）→ H → I | 医用级信任→慢病管理链路→私域随访 |
| **汽车4S店（整车+售后）** | A → C → D → F（售前→交付→售后）→ H → K | 车主旅程→营销增长 |
| **区域经销商（B2B为主）** | A → B → G → I → H | 现状诊断→赋能体系→私域→产品落地 |
| **技术驱动型大客户** | A → D → E → L → H → N → M | 突出AI技术架构和系统设计 |
| **连锁加盟（单店模型清晰）** | A → B → G（单店赋能模板）→ J → H → M | 强调可复制性 |
| **3C数码品牌（多平台即时零售+多供应商）** | A → D → F（五阶段全链路）→ J + K → H → M | 即时零售主赛道+多供应商分账履约；参考联想案例（3800门店） |
### 4.5 使用示例

```
输入：零售品牌方（50+门店，多平台管理痛点，业务负责人决策）
→ A + D + F2 + J + H + K
→ 6个章节：行业→痛点→全渠道中台（核心）→会员→产品→增长

输入：零售品牌方（多平台管理痛点，CTO参与决策）
→ A + D + F2 + L + H + N
→ 6个章节：行业→痛点→全渠道中台→AI技术架构（替换私域/会员）→产品→技术设计

输入：美业连锁（10家店，门店管理痛点，老板决策）
→ A + C + D + F + G + J + H + M
→ 8个章节：追加B端赋能和实施路径稳老板信心
```

## 五B、全渠道2.0跃迁专项模块（零售行业专用）

> **来源：** 微盟Weimob Day 0422 · 凌芸《零售无界·沉浸共生》终稿

当客户属于**零售行业**且具备以下特征时，自动启用本模块：

- 存在渠道割裂痛点（商品重复上架、库存不同步、订单分散、券核销复杂）
- 从"卖商品"向"商品+服务"转型

### 全渠道1.0 → 2.0 跃迁框架

| 维度 | 1.0（现状） | 2.0（目标） |
|-----|------------|------------|
| **经营渠道** | 单一/独立运营 | 多渠道并行：天猫、淘宝、抖音、小红书、美团闪购、本地生活平台、即时零售平台 |
| **商品形态** | 实物销售为主 | 实物商品 + 团购券/优惠券 + 服务类商品 |
| **业态延展** | 卖商品 | **商品+服务** |
| **运营模式** | 各渠道独立运营 | 业务中台一体化统筹 |
| **用户经营** | 流量获取 | 用户价值深耕（LTV） |

### 四大中台打通方案

| 中台 | 痛点对应 | 核心能力 | 效果 |
|-----|---------|---------|------|
| **商品中台** | 商品重复发布 | 统一配置·一键分发多平台 | 减少重复上架与维护 |
| **库存中台** | 库存无法同步 | 全渠道共享一盘货·实时同步 | 避免超卖与库存积压 |
| **订单中台** | 订单处理复杂 | 多渠道统一接入·自动化履约·状态实时回传 | 减少人工干预，降低错/漏发风险 |
| **营销中台** | 券核销链路复杂 | 多平台券统一生成·小程序统一核销 | 简化核销流程，提升用户体验 |

**最终效果：** 微盟系统 → 业务中台一体化 → 多平台一站式统筹 → 减少重复作业，提升运营一致性与效率

## 七、输出策略（重要更新 v5.3）

> **2026-05-13 更新：服装行业方案输出实践（两次AI PPT失败 + 一次自建HTML重构通过）**

### 输出优先级

| 优先级 | 工具 | 适用场景 | 质量表现 |
|-------|------|---------|---------|
| **P0** | SmartCanvas（腾讯文档AIO） | 客户汇报、管理层阅读、详细方案 | ✅ 精美排版，Callout/分栏/表格丰富，结构清晰 |
| **P1** | HTML自建演示 | 正式路演、客户汇报 | ✅ **信息密度全控**，15页完整方案，~40KB/千行内 |
| **P2** | PPT（腾讯文档Slide） | 仅当用户明确要求PPT格式 | ❌ 实测两次被拒：排版空洞、内容干瘪、空置率高 |
| **P3** | Markdown纯文本 | 内部参考、快速输出 | 轻量，视觉呈现弱 |

### ⚠️ PPT生成质量陷阱（实测 2026-05-13，两次验证+一次HTML重构后通过）

**现象**：用户连续两次拒绝AI PPT，具体反馈：
1. **排版过于简单** — 只有标题+几行bullet，无卡片/表格/流程图等多样元素
2. **内容空置率很高** — 每页超过一半区域是空白
3. **内容填充少** — 完整章节被压缩到2-3句话，信息密度极低

第二次用更详细的描述重新提交后，结果依然被同样批评。

**根本原因**：AI PPT生成（腾讯文档Slide）是**黑盒模板引擎**，无法控制排版密度、字号、布局。完整方案内容被模板强制压缩，不是通过调整输入就能解决的。

**正确工作流**：

```
方案内容（Markdown完整版）
    │
    ├── P0: SmartCanvas 文档（腾讯文档AIO）
    │   精美排版，分栏/Callout/表格/高亮块
    │   适合客户汇报、管理层阅读
    │
    ├── P1: 用户要求PPT时 → 优先尝试 SmartCanvas Slide
    │   成功（结果精良）→ 直接交付
    │   失败（被批评空洞/稀疏）→ 降级到 HTML 演示
    │
    ├── P2 降级方案一：自建HTML演示（推荐，已验证通过）
    │   完全手写，布局/密度/风格全控
    │   详见下方"HTML演示方案"
    │
    └── 降级方案二：PptxGenJS手写PPT（备选，尚未实际使用）
        Node.js环境生成.pptx
        详见 references/urban-ppt-example.md
```

### 降级方案一：自建HTML演示（推荐，已验证通过）

**最佳实践**：2026-05-13 URBAN女装方案。AI PPT两次被拒后，手写HTML演示稿（41KB，15页，1068行）一次性通过验收。

**设计规范**（可直接复用模板）：

| 要素 | 规范 | 说明 |
|-----|------|------|
| 配色 | 深色商业风 | 背景 `#0f0f13`，卡片 `#1a1a24`，强调 `#6c5ce7`(紫)+`#fd79a8`(粉)+`#00b894`(绿) |
| 布局 | 全屏卡式 | 每页60-80px内边距，内容在卡片内居中，不溢出 |
| 字体 | Noto Sans SC | Google Fonts CDN加载，权重300/400/500/700/900 |
| 翻页 | 键盘←→ + 触屏滑动 | touchstart/touchend手势检测 |
| 页码 | 每页右下角 | 格式 `N / M total` |
| 来源标注 | 每页右上角 | 来源：[知识库文件名] |

**内容密度要求（每页）**：
- 1-2个标题级 + 2-5个内容块（表格/卡片网格/流程图/时间线/矩阵/轮播）
- 正文总字数200-600字
- 不留大面积空白（>30% = 不合格）
- 元素交替布局，不重复同一样式

**技术选型建议（HTML vs PptxGenJS）**：

HTML > PptxGenJS，原因：
- HTML可精确控制每个像素，PPT模板做不到
- HTML翻页动画/触屏支持天然具备
- 修改直接改HTML秒级生效，无需重新生成
- 无需安装Node.js依赖

**复用指南**：
1. 从 `templates/html-presentation-template.html` 复制模板
2. 替换 `slides` 数组中的每页内容（保留结构）
3. 配色微调（行业主色+品牌色）
4. 部署后用 Python HTTP server 本地预览

### 降级方案二：PptxGenJS 手写PPT（备选，尚未使用）

## 九、输出约束条件（重要！必须遵守）

### 绝对禁止

1. ❌ **禁止编造数据**：没有知识库依据的效果指标（百分比、绝对值）不得出现在方案中
2. ❌ **禁止胡乱搭配**：产品组合必须基于知识库中有据可查的版本体系
3. ❌ **禁止过度承诺**：不得承诺超出微盟产品能力的功能
4. ❌ **禁止套用错误行业**：每个行业的痛点和方案必须匹配，不能张冠李戴

### 替代方案

| 场景 | 正确做法 |
|-----|---------|
| 需要效果指标 | 用定性描述，如"显著提升"、"有效解决"，不写具体数字 |
| 没有标准版本的行业（大健康等） | 注明"具体产品配置待需求确认后由售前团队提供" |
| 不确定的产品能力 | 注明"需确认是否支持"或"建议与产品团队确认" |
| 需要报价 | 注明"具体报价由商务团队沟通" |

### 审核要点

生成方案后，必须自查：

- [ ] 行业痛点是否与该行业实际匹配？
- [ ] 微盟产品能力是否真实存在（非编造）？
- [ ] 是否有具体的数字指标（若有，来源是否可查）？
- [ ] 产品组合是否符合版本体系或有明确说明？
- [ ] 语言表达是否符合微盟官方表述？

## Umbrella Section — 阿信多智能体协作流水线（吸收自axin-pipeline）

> **对应归档技能：** axin-pipeline — `/axin <任务描述>` 启动四角色协作流水线

solution-framework v4.0时已将axin-pipeline的核心机制融合进自身的四阶段协作流程。本节记录原始设计来源，供深度参考。

### axin-pipeline 原始设计

```
用户任务
   ↓
① 参谋长（战略规划）
   ↓
② 调度长（任务拆解）
   ↓
③ 执行长（落地执行）
   ↓
④ 审核官（质量评审）
   ↓
最终交付
```

**四角色原始定义：**
- ① **参谋长**：全局战略总谋，顶层架构设计师。输出：问题本质定义、顶层架构/方案、关键里程碑、风险与备选、下一步行动建议。
- ② **调度长**：全域事务中枢，任务时序管理者。输出：任务清单（优先级P0/P1/P2/P3）、时间节点、依赖关系。
- ③ **执行长**：高效落地执行者。输出：执行状态、产出物详情、下一步计划。
- ④ **审核官**：规范质检，输出标准管控。输出：整体评价+评级、逻辑校验意见、格式规范意见、优化建议、最终交付物。

**solution-framework中的对应：** solution-framework的四阶段（参谋长→调度长→执行长→审核官）直接继承自axin-pipeline的原始设计，已无缝融合。

## 附：PPT输出流程（飞书腾讯文档MCP）

> **经验来源：** 2026-05-13 URBAN女装方案输出

### 工具链

| 步骤 | 工具 | 说明 |
|-----|------|------|
| 1 | `mcp_tencent_docs_create_slide` | 提交PPT生成任务，返回 `session_id` |
| 2 | `mcp_tencent_docs_slide_progress` | 轮询进度，传入 `session_id` |
| 3 | 返回 `status: "completed"` + `file_url` 时完成 | 取 `file_url` 给用户 |

### ⚠️ Pitfall：长等待模式

**现象：** `slide_progress` 返回 `status: "in_progress"` 会持续多次（本次实测10+次，约6分钟）。

**错误做法：** 短间隔（5-10秒）高频轮询，既浪费调用次数又可能触及限流。

**正确做法：**
```python
# 首次轮询：10秒后
sleep(10)
progress = mcp_tencent_docs_slide_progress(session_id)

# 如果仍是 in_progress，后续轮询间隔至少 30-60 秒
if progress.status == "in_progress":
    sleep(30)
    # 依此类推，60秒为安全间隔
```

**判断完成：** 看到 `status: "completed"` + `file_url` 有值即为成功。

### 复用时的检查清单

- [ ] `reference_context` 传入了完整的方案框架 Markdown
- [ ] 设置了合理的 `description`（用户可见）
- [ ] 轮询间隔符合上述 Pitfall 规则
- [ ] 完成后将 `file_url` 以链接形式返回给用户
